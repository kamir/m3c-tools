CISO onboardingskillctl — the trust layer for agent skills honest by design

Arm the CISO to defend skillctl — to a hostile security expert and a picky CTO

Every agent skill is arbitrary code that runs with your agent's full permissions, and today that supply chain is unsigned, unreviewed, and unrevocable. skillctl closes the provenance + governance + integrity + revocation half of that problem — and is deliberately honest about the half it does not (the runtime cage). The deck wins by conceding the real limit, then holding the defensible core with exact evidence.

Lead argument #1

No hosted CA in the verdict path. A different principal verifies the whole chain with your pinned ed25519 roots + the bundle bytes alone — no OCSP / CRL / Rekor / Fulcio call to reach a verdict. If we disappear, verification still works.

Lead argument #2

reviewer≠author, enforced in cryptography. Separation-of-duties as a pinned-key floor across distinct principals. A stolen author key still can't manufacture a green review; a red→green sidecar edit fails closed.

Lead argument #3

Honest, fail-closed scope. We sell the provenance+governance+integrity+revocation lock now, and explicitly not the runtime cage (FR-0044, roadmap). The PreToolUse gate shrinks what reaches ambient authority — it doesn't confine it.

1The hole: a skill is code with your agent's keys

An agent skill isn't a library you might call — it's arbitrary code the agent executes on its own initiative, with the agent's full permissions. Today that supply chain is unsigned, unreviewed, and unrevocable.

  • A poisoned or swapped skill = SolarWinds / xz / npm-typosquat — but the payload runs with the agent's ambient authority, not yours.
  • Today's default: no author identity, no independent review, no integrity check, no way to revoke a known-bad skill fleet-wide.
  • The realistic vector is data-borne: a skill pulled from a room, imported from the internet, shared cross-person — no attacker code-exec on your box required.
"If your risk register carries dependency-confusion as a real line, agent skills are that line — with the safety off."

2Threat model: what actually reaches invocation

Rank by likelihood, not movie-plot. The common vector is a tampered / forged / revoked / under-reviewed skill entering as data — exactly the population skillctl removes from the board.

Stated up front as out of scope: an attacker who already has same-uid write in the agent's config dir — a truism about the OS boundary, not a skillctl defect.

3The answer: a three-signature chain over a content-addressed digest

Bundle identity = sha256 of a deterministic archive. Three distinct pinned principals sign over that digest: author ("who wrote it"), registry ("admitted on this date"), governance ("a named reviewer set the level"). The verifier recomputes the digest and never trusts the advertised one.

  • Same primitive TUF and Sigstore sign with — no novel crypto. The value claim is narrow and true: three distinct pinned principals, not "three files on one box" (that's an operator error, not the design — see Slide 8).
  • Reproducible digest, scoped honestly: byte-for-byte reproducible with the same skillctl pack (pinned version, deterministic PAX tar + gzip --no-name). Gzip output is toolchain-dependent, so the cross-implementation content check is the per-file CHECKSUMS manifest.

4Differentiator #1 — no hosted CA in the verification path

A different principal verifies the full chain with pinned ed25519 roots + the bundle bytes alone — no OCSP, CRL, Rekor, or Fulcio call to reach a verdict. Even revocation is a signed, pinnable offline list, not a network lookup.

Hosted-CA modelskillctl offline model
A permanently-online, permanently-attackable issuance authority that can mint a valid cert for your fleet on any day, not just day-zero. The trust root is yours — a key you generate and hold. verify.go pinned-author mode does ed25519.Verify against a local key with zero registry calls.
"Sigstore proves where a public binary came from in the open; skillctl proves a skill's provenance+governance+integrity to an offline verifier who pins their own root."

Reconciled with revocation (Slide 6): the verdict computation is offline. Revocation freshness has a distribution SLO over any channel you already run (MDM / git / S3); "brick-on-stale" for high-risk actions is intended fail-closed, not a network dependency in the crypto. Low/no-risk verification stays fully offline.

5Differentiator #2 — reviewer≠author, enforced in cryptography

The "only reviewer is the author" laundering weakness is closed by a signature-verified attestation from a pinned reviewer whose id differs from the verified author. A forged unsigned reviewer_id can't launder past the floor; a stolen author key still can't manufacture a green review.

6Differentiator #3 — fail-closed revocation + freshness with a rollback floor

A stale, replayed, or rolled-back revocation view cannot authorize a high-risk action. Past max_staleness, HIGH-risk always fails closed regardless of config; a monotonic signed-epoch floor refuses an older genuinely-signed list; the clock is injected so a replayed stale list can't masquerade as fresh.

  • freshness.go PolicyFor(): RiskHigh → FailClosed is an invariant — validation refuses to even configure high-risk fail_policy=open.
  • Risk classifier is a closed allowlist (knownLowRiskTokens): an unknown / mistyped / creatively-labelled action is HIGH by exclusion — an author can't "declare read-only" into fail-open.
  • revocation.go minEpoch: a list below the pinned epoch floor is refused even with a valid signature (TUF anti-rollback idea).
  • Future-dated / unparseable issued_at → treated as infinitely stale (fail-safe, not fail-random).

7Every failure is a numbered exit code — CI-branchable, SIEM-portable

The verify/install CLI exit is a stable integer CI can branch on (os.Exit(verify.ExitCode(err))) — no bespoke stderr parser. Codes are not injective: overloaded numbers (12, 17) are disambiguated by label/surface; the PreToolUse hook exits 2 to block while carrying the numbered code in its output.

8Objections you'll hear — the security expert

Win by conceding the real limit first, then holding the defensible core with exact evidence. The concessions are what make the rebuttals credible — never bluff.

ObjectionConcedeRebut
Software keys, no HSM — three signatures are three cat-able files True: ed25519 PEM at 0600; no HSM/threshold yet. You've conflated key storage with key co-location. The value is three distinct principals — a stolen author key still can't forge a green reviewer signature. Release custody is already keyless (Sigstore/OIDC, no laptop key). HSM/threshold for the registry root is a named roadmap gate, not a claim we make today. verify.go verifiedIndependentReviewer()
Provenance ≠ safety — you prove who, never what it does Dead right: crypto proves who signed + that bytes are unchanged, not runtime behaviour. So don't buy it as behavioural safety — buy the layer that makes behavioural defense possible & accountable: (1) attribution — when a sleeper detonates, you know exactly which author+reviewer signed which digest (a lookup, not a forensic dig); (2) revocation has teeth — fail-closed, tested. (bodyscan is advisory/unproven — we claim no credit for it.)
No runtime cage — you gate a knife then hand it over handle-first Conceded: FR-0044 is PENDING; a passed skill runs with ambient authority. The compensating control is real and fail-closed: the PreToolUse hook hardens the entry — unsigned/tampered/revoked/self-reviewed skills never reach invocation (panic-safe DENY on any error). It is not self-protecting against same-uid tampering after execution — that is exactly the FR-0044 gap, named not hidden. A seal that refuses to open when broken is worth money before the walls ship.
TOFU root bootstrap — your root of trust is a YAML file; how did it arrive? Sharp and fair: the first pin is trust-on-first-use; we relocated "trust the CA" to "trust the first pin". But TOFU-once beats a standing CA for a security org: a hosted CA also has to bootstrap its root to the endpoint, and adds a permanently-online authority that can betray you any day. Our pin rides your existing MDM / signed-image / provisioning channel — one authenticated moment vs a perpetual attack surface.
No transparency log — offline = undetectably compromisable Correct in pure-offline config: pinned-roots-only gives no external post-compromise witness. That's a configuration, not a ceiling: log-inclusion is a shipped opt-in — set require_log_inclusion and the verifier fails closed (exit 23) with no valid inclusion proof under a pinned Signed Tree Head. "Offline by default, log-witnessed by policy."
Registry key = its own revocation — steal it, own the kill-switch The genuine structural weak point, named precisely: the revocation feed is signed by the key it protects. The epoch floor still blunts the 2am case: an attacker with the key can suppress a revocation but cannot roll an existing fleet backward to un-revoke (clients that saw epoch N refuse anything below N). In-band threshold/timestamp-role recovery (TUF-style) is on the roadmap, named as a sign-off condition — not claimed as present.
You reinvented TUF/in-toto — uncited, un-analyzed crypto Partly landed: bespoke ed25519 framing + epoch scheme, no external formal-analysis paper on our exact composition. The honest framing is "layers on where the standard fits, diverges only where a mandatory online log is a liability, reuses their audited ideas": release provenance = Sigstore/cosign directly; three-sig = in-toto layered attestation; epoch floor = TUF anti-rollback; raw ed25519 = the same primitive both sign with. External crypto review of the canonicalization is a named sign-off condition.
Governance theater — an attestation is a signature over "trust me" True: a signature proves the authenticity of a claim, never its truth; the attestation embeds no scan/diff evidence today. It's not bare: the verdict is bound to the exact digest under review and re-verified against a pinned reviewer key — "trust me, about this digest, and I can't lie about which." Binding richer evidence (scan hash, policy id) into the signed message is a named enhancement, not a reinvention.

9Objections you'll hear — the CTO

The CTO probes cost, bus factor, lock-in, and "why not wait for the standard." Same discipline: concede the operational truth, then show what the offline design deliberately deletes from the TCO.

ObjectionConcedeRebut
Single maintainer / bus factor True — the git log shows one author on the trust core; a single-maintainer dependency on a fail-closed path is a real risk. De-risked without waiting for a second committer: it's an offline verifier with no server to keep alive — the core sig+digest check is small, and the full offline verifier (freshness, signed-revocation, rollback-floor, tenant, trust-roots, transparency-log) is ~4.2k LOC of test-covered stdlib-crypto Go. Fork-and-pin + a second committer are named sign-off conditions. If the maintainer vanishes, your pinned root keeps verifying.
Real TCO isn't $0 Conceded: key custody/rotation for three tiers, a registry to keep, reviewer workflow, responder training — an operational program, not a download. Price it honestly — then notice what the design doesn't put on your books: no always-on HSM-backed CA, no OCSP service; the registry is not in the verification path, so a registry outage doesn't hard-block verification. The expensive part of classic PKI is architected out.
Lock-in / single-vendor trust root Fair one layer up: your operators learn skillctl, pipelines emit .skb, CI policy speaks its exit codes. The trust root is yours, not ours — you pin your own key and verify with no vendor CA. .skb is a standard gzip-tar + ed25519, re-serializable; the exit path is CI glue, not a rewrite. Transport is carrier-agnostic (ER1 / GCS-MinIO / OCI as peers).
Why not wait for the OpenSSF/MCP standard? The category is ~18 months old; a standard attestation format may converge. We're built on the primitives any standard will use (content-addressing, detached sigs, in-toto layering, TUF anti-rollback), so we're the low-regret bet, not the stranded one — meanwhile every unsigned skill runs with agent permissions today. Adopt the reversible parts now (pin your own root, CI exit codes); the .skb→SPDX/in-toto export is a named roadmap item.
Does it move an audit line? (SOC2 / AI-Act) There's no auditor checkbox named "skillctl"; we position AI-Act as evidence, not a compliance stamp. It maps to named controls as evidence you can hand an auditor: SOC 2 CC8.1 (change mgmt) + CC7.x (unauthorized-change detection) via the tamper-evident digest + three-sig chain; cryptographic reviewer≠author for segregation-of-duties. Stronger than ad-hoc signing on the two axes auditors actually probe.
Is this a real problem or theater? Honest: I can't hand you a named public breach of a signed-skill supply chain that this uniquely stopped — the surface is new. The risk is theoretical only in label: it's the supply-chain class with named public incidents (SolarWinds, xz/liblzma, npm/PyPI typosquats) — now pointed at a payload that runs with the agent's permissions. The reversible Phase-1 spend is small; the downside of waiting is unsigned code with ambient authority.

10Honest scope — what it is, what it is not

The deck wins by drawing this line in ink. Overclaiming loses a sharp reviewer.

✓ skillctl IS

  • A provenance layer — content-addressed .skb identity binds a version to a signing author + admission.
  • A governance layer — a reviewer's Ampel verdict is a signed attestation, reviewer≠author cryptographically enforceable.
  • An integrity layer — any post-signing byte change breaks the digest; tamper-evident, fails closed.
  • Offline third-party verifiable — pinned roots + bytes, no hosted CA / log / network in the verdict.
  • A fail-closed revocation + freshness system (signed lists, epoch floor, staleness contract).
  • A CI-gateable surface — numbered exit codes (10–23).

✕ skillctl is NOT

  • A runtime sandbox / OS capability cage — that is FR-0044, PENDING. The hook gates whether a skill may be invoked; it does not confine it.
  • A behavioural-safety proof — bodyscan is a static heuristic (≥95% TP / ≤5% FP target, unproven), not a guarantee.
  • A hosted-CA / online-CRL model.
  • Yet hardened for arbitrary untrusted multi-party fan-out beyond the pinned-key + co-learning-room model.
  • A replacement for Sigstore/SLSA/in-toto/TUF — it layers on them (Slide 11).
Compensating control today: the fail-closed PreToolUse verify-hook shrinks the population reaching ambient authority to exactly the signed + attested + non-revoked + attributable set. It hardens the entry; it is not self-protecting against same-uid tampering post-execution — that is the FR-0044 gap.
"I'm selling you the gate now and the cage on the roadmap — and I'm pricing it as exactly that."

11How it layers — Sigstore / SLSA / in-toto / TUF

skillctl doesn't reinvent the ecosystem: it uses the standard where a public artifact fits, diverges only where a mandatory online log is a liability, and reuses the standards' audited ideas everywhere else.

Public release artifact → standards, directly

cosign keyless + GitHub OIDC (no key on any laptop), SLSA build-provenance (gh attestation verify → 0), CycloneDX SBOM. Flows straight into your existing supply-chain tooling.

Sovereign skill bundle → diverges by decision

The bundle chain deliberately does not depend on Rekor/Fulcio in the verdict path (SPEC-0188 D1 — a decision, not an oversight). That is the offline-sovereign differentiator.

Ideas reused

Three-sig chain = in-toto layered attestation; monotonic-epoch floor = TUF anti-rollback; raw ed25519 = the primitive both sign with. Rekor-style transparency is opt-in (exit 23) under a pinned Signed Tree Head.

13The ask — adopt the lock now, roadmap the cage

Approve a scoped, phased rollout that gates the realistic supply-chain vector today, with maturity conditions and the runtime cage named as the next layer — not oversold as present.

Phase 1 — adopt now (reversible)

Pin your own ed25519 root via MDM / signed-image; turn on the fail-closed PreToolUse hook; wire exit codes 10–23 into CI + SIEM.

Sign-off conditions (owned, not hidden)

2nd committer + fork-and-pin runbook; a line-item 3-year TCO model; measured block-rate as an SLI before any revenue-path agent; tiered review policy.

Named next layers

FR-0044 OS-level cage; TUF-style timestamp/threshold role for registry-key recovery; external crypto review of the freshness canonicalization; .skb → SPDX/in-toto export.
